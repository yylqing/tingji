## 0. TL;DR

**热词不是一个开关，是三层互补的机制**。实测同一段含专名的音频：

| 方案 | `沈知微` | `河坊街` | 耗时（9.33s 音频） |
|---|---|---|---|
| 无热词（基线） | 沈志威 ❌ | 和房街 ❌ | 0.43s |
| **L1 模型级偏置**（SeACo hotword） | **沈知微 ✅** | 和坊街 ❌ | 0.48s |
| **L2 文本级后处理**（拼音模糊替换） | **沈知微 ✅** | **河坊街 ✅** | 0.49s |

三层各自解决不同问题，**任何一层单独用都不够**：

| 层 | 作用点 | 能解决 | 解决不了 | 成本 |
|---|---|---|---|---|
| **L1 模型级偏置** | 解码时 | "听成别的音"（沈志威→沈知微） | 偏置是软的，改不彻底（和坊街） | 几乎为 0（+0.05s） |
| **L2 文本级后处理** | 解码后 | "音对了但字错"（和坊街/和房街→河坊街） | 音差太远（完全没听出来） | 微秒级，可上千条 |
| **L3 LLM 术语表** | 语义层 | 上下文能推断的错误、代词/性别 | 不能凭空造出没听到的音 | 已有纠错阶段，无增量 |

**产品结论**：登记一次热词，同时注入三层；L2 是"保底承诺"——只要读音沾边，最终文本一定写成你登记的写法。

---

## 1. 为什么必须做热词登记

ASR 的词表是封闭的（Paraformer 中文词表 8404 类 BPE，MOSS 依赖解码器先验），**长尾专名必然出错**。而我们的场景里长尾词密度极高：

| 类型 | 例子 | 为什么模型会错 |
|---|---|---|
| 人名 | 沈知微、覃（qín）磊 | 训练集里没有，且姓名字音组合罕见 |
| 地名 | 西溪湿地、河坊街、爨底下村 | 多音字、生僻字 |
| 宠物名 | 豆豆、皮蛋、年糕 | 与日常词同音，模型会"归化"成常用词 |
| 项目名 | 数据中台三期、灵犀 | 内部造词 |
| 英文专名 | ClickHouse、Kubernetes | 中文声学模型对英文发音弱（实测识别成"认批""标准查询"） |

这些词恰好是**纪要里最重要**的词（谁、在哪、哪个项目）。错一个，整段纪要的可信度就掉了。

> 实测：不加任何处理时，`沈知微 → 沈志威`、`河坊街 → 和房街`、`ClickHouse → 认批`。

## 2. 三层注入机制

```
                    ┌──────────────────────────────┐
  热词库（SQLite）──┤  L1 模型级：SeACo bias /     │──▶ 解码器偏置
                    │      MOSS prompt 热词         │
                    ├──────────────────────────────┤
                    │  L2 文本级：pinyin 模糊匹配  │──▶ 文本替换（0.85 阈值）
                    ├──────────────────────────────┤
                    │  L3 语义级：LLM 纠错术语表    │──▶ 上下文纠错
                    └──────────────────────────────┘
```

### 2.1 L1 模型级偏置

**FunASR（主引擎）**：SeACo-Paraformer 支持 `hotword` 参数，在解码时对热词的首 token 做奖励。

```python
model.generate(input=wav, hotword="沈知微 河坊街 豆豆 ClickHouse", ...)
```

- 优点：真正影响"听"的结果，能救回基线听错的词。
- 缺点：**软偏置**。实测把"沈志威"救回"沈知微"，但"和房街"只变成"和坊街"（没到标准写法）。
- 建议上限：**≤ 50 条**（过多会稀释偏置强度，且拖慢解码）。

**MOSS（重叠段/高质量模式）**：默认 prompt 后追加 `热词提示：词1, 词2, …`。

```python
PROMPT + "热词提示：沈知微, 河坊街, 豆豆"
```

- 实测：`沈志威 → 沈知微`，且顺带把"他家的"改成"她家的"（语义层受益）。
- 缺点：prompt 变长，token 成本上升；条目过多会挤占上下文。

### 2.2 L2 文本级后处理（本设计的核心）

FunASR 1.4.17 内置 `postprocess_hotwords`：**解码后**用 拼音 + rapidfuzz 做模糊匹配替换。

```python
model.generate(
    input=wav,
    postprocess_hotwords={"沈志威": "沈知微", "和房街": "河坊街"},  # 显式别名
    postprocess_hotword_threshold=0.85,          # 默认 0.85
    return_postprocess_hotword_matches=True,     # 返回每处修正，便于 UI 展示
)
```

**实测语义**（直接调用 matcher）：

```
输入: 沈志威带着豆豆去了和房街。
输出: 沈知微带着豆豆去了河坊街。
修正: 沈志威 -> 沈知微 (1.00)
      和房街 -> 河坊街 (1.00)
```

- **显式别名表**（`错写法 => 标准写法`）命中即 1.0 分；
- **纯拼音模糊**：`沈知微` vs `沈志威`、`河坊街` vs `和房街` 拼音键相同（**不区分声调**）→ 也命中 1.0；
- 这意味着**用户只需登记标准写法，同音错字自动被拉回来**——这正是"登记一次、长期生效"的关键。

**为什么 L2 是关键**：

1. **确定性强**：L1 是概率偏置，L2 是规则替换，只要音近就一定写成你要的样子。
2. **成本近乎为零**：纯 CPU 字符串匹配，实测 0.48s → 0.49s（+0.01s/9.3s 音频）。
3. **可扩展到上千条**，不受解码预算限制。
4. **可解释**：能返回"哪一处、从什么改成什么、置信多少"，UI 可以展示与撤销。

**风险**：过度替换。`豆豆` 也可能出现在"都都""兜兜"等正常语境里。缓解：阈值 + 最小长度 + 仅拼音键相同才替换 + 误报统计（用户撤销即降权）。

### 2.3 L3 LLM 术语表

已有的纠错阶段（PRD FR-D3）把热词作为术语表注入 prompt，负责语义层：代词性别、上下文拆分、明显笔误。

**注意**：LLM 可能把已经改对的词又"纠"回去，所以 **L2 要在 LLM 纠错之后再跑一遍**（幂等，代价可忽略）。

## 3. 实测证据

### 3.1 测试音频

TTS 合成 9.33s：
> 沈知微上个周末带着她家的柯基豆豆去了杭州西溪湿地，中午在河坊街的一家叫半亩方塘的小馆子吃饭。

真值专名：`沈知微 / 柯基 / 豆豆 / 杭州西溪湿地 / 河坊街 / 半亩方塘`

### 3.2 FunASR 三层对比

| 层 | 输出 | 专名命中 |
|---|---|---|
| 基线 | 沈志威…柯基豆豆…杭州西溪湿地…**和房街**…半亩方塘 | 4/6 |
| L1 模型级 | **沈知微**…柯基豆豆…杭州西溪湿地…和坊街…半亩方塘 | 5/6（写作仍不对） |
| L2 文本级 | **沈知微**…柯基豆豆…杭州西溪湿地…**河坊街**…半亩方塘 | **6/6** |

耗时：0.43 / 0.48 / 0.49s（RTF 0.046 / 0.051 / 0.053）。

### 3.3 MOSS 对比

| 层 | 输出 | 命中 |
|---|---|---|
| 无热词 | **沈志威**…他家的柯基豆豆…河坊街…半亩方塘 | 5/6（人名错、代词错） |
| 加 prompt 热词 | **沈知微**…**她**家的柯基豆豆…河坊街…半亩方塘 | **6/6** |

耗时：5.79s（1.61× 实时）。

> 观察：MOSS 基线对地名本来就比 Paraformer 强（河坊街一次就对），但对人名同样无能为力——**人名/宠物名这类"不在词表里"的词，任何模型都需要热词**。

### 3.4 结论

1. **L2 必须做**，它是"写入正确写法"的唯一保证，而且几乎免费。
2. **L1 要做**，它能把"完全听错"拉回可匹配范围（否则 L2 的模糊匹配也够不着）。
3. **L3 复用已有纠错**，不需要新增环节。
4. 三层叠加后，本样本从 4/6 到 **6/6**。

## 4. 数据模型

```sql
CREATE TABLE hotwords (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  term        TEXT NOT NULL,              -- 标准写法（最终要出现在文本里的样子）
  pinyin      TEXT,                       -- 自动生成，可手工覆盖（多音字用）
  type        TEXT,                       -- person|place|org|project|product|pet|english|other
  aliases     TEXT,                       -- JSON: ["沈志威","沈志微"] 常见误写
  weight      REAL DEFAULT 1.0,           -- 0.1–2.0，影响 L1 偏置强度与 L2 优先级
  scope       TEXT DEFAULT 'global',      -- global | project:<id>
  enabled     INTEGER DEFAULT 1,
  source      TEXT,                       -- manual|bulk_import|auto_discovered|obsidian
  note        TEXT,
  created_at  TEXT,
  updated_at  TEXT
);

CREATE UNIQUE INDEX ux_hotwords_term ON hotwords(term);

-- 命中统计（用于治理：命中多→保留，误报多→降权/停用）
CREATE TABLE hotword_stats (
  hotword_id  INTEGER,
  job_id      TEXT,
  layer       TEXT,                       -- L1|L2|L3
  matched_at  INTEGER,                    -- 字符位置
  original    TEXT,                       -- 被替换的原文
  score       REAL,
  reverted    INTEGER DEFAULT 0,          -- 用户撤销 = 误报
  created_at  TEXT,
  PRIMARY KEY (hotword_id, job_id, layer, matched_at)
);
```

**别名字典的来源**（自动积累）：

1. 用户手工填写；
2. **从 LLM 纠错 diff 中反推**：若纠错把 `X` 改成热词 `T` 且 `X` 与 `T` 拼音相近 → 把 `X` 写入 `aliases`；
3. 从 L2 的 `hotword_matches` 里反推（`original → replacement`）。

## 5. Web 登记设计（`/hotwords`）

### 5.1 列表页

```
┌───────────────────────────────────────────────────────────────┐
│ 热词库    [+ 新建] [批量导入] [从纠错中导入] [试一段]           │
│ 筛选：全部 / 人名 / 地名 / 宠物 / 项目 / 英文   搜索 [      ]   │
├───────────────────────────────────────────────────────────────┤
│ 沈知微     人名   别名 沈志威·沈志微   命中 12  误报 0   [编辑]│
│ 河坊街     地名   别名 和房街·和坊街   命中 8   误报 0   [编辑]│
│ 豆豆       宠物   别名 —               命中 15  误报 1 ⚠️[编辑]│
│ ClickHouse 英文   别名 认批·克力克豪斯 命中 6   误报 0   [编辑]│
└───────────────────────────────────────────────────────────────┘
```

- 顶部统计：热词总数、本月命中、误报率、未生效条目（从未命中）。
- 误报率 >10% 的条目自动标 ⚠️ 并建议降权。

### 5.2 新建 / 编辑

```
标准写法 *  [ 沈知微            ]   ← 最终出现在文本里的样子
类型       [ 人名 ▾ ]
别名/误写   [ 沈志威, 沈志微    ]   ← 逗号分隔，可留空（靠拼音自动匹配）
拼音       [ shen zhi wei      ]   ← 自动生成，多音字可改
权重       [ 1.0 ]  (0.1–2.0)
适用范围   [ 全局 ▾ / 项目：数据中台 ]
备注       [ 同事，常出现在周会     ]
☐ 同时在 Obsidian 创建人物笔记，并关联声纹注册
```

### 5.3 批量导入

- **粘贴**：一行一个，支持 `词` 或 `词,类型` 或 `词=>别名1,别名2`；
- **CSV/JSON 上传**；
- **从 Obsidian 人物笔记同步**：扫描 `人物/*.md` 的标题与 `aliases` 字段；
- 导入前**预检**：重复、与已有词拼音冲突、类型缺失，逐条给结论。

### 5.4 试一段（关键体验）

登记完不知道有没有用，是最常见的挫败点。提供：

```
[录制 10 秒] 或 [上传音频]
→ 输出：原文（无热词）vs 生效后（有热词）
→ 高亮每处修正，可点"撤销这条修正"
```

后端就是用两遍 `generate`（一次不带热词、一次带），差异对比即可。成本约 2×（9s 音频 ≈ 1s）。

### 5.5 从纠错中导入（自动发现）

纠错阶段会产出 diff。若某个"原文→改后"模式在最近 N 个任务里出现 ≥2 次，且改后词在原文中反复出现 → 在 `/hotwords` 顶部提示：

```
发现 3 个候选热词：灵犀（出现 5 次）、数据中台三期（3 次）、西溪湿地（2 次）  [一键加入]
```

## 6. 生效策略与配额

| 项 | 策略 | 理由 |
|---|---|---|
| L1 条数上限 | 默认 **50 条**（按 weight 降序取） | 偏置会稀释；实测过多无收益且拖慢 |
| L2 条数上限 | **2000 条** | 纯字符串匹配，成本可忽略 |
| L3 注入 | 按**批次相关**筛选（只注入本批出现过的候选 + 全局高频） | 省 token，避免无关词干扰 |
| 优先级 | 同一别名冲突时，`weight` 高者胜；仍冲突则报错要求人工裁决 | 防止 `豆豆` 被替换成别人的宠物名 |
| 范围 | `global` / 按项目；任务可按标签匹配项目 | 不同客户/项目的人名互不干扰 |
| 最小长度 | L2 只对 **≥2 个汉字或 ≥4 个字母** 的词做模糊替换 | 单字替换误伤极高 |
| 阈值 | L2 默认 0.85（拼音键完全一致即 1.0） | 平衡召回与误报 |
| 开关 | 全局开关 + 单条启用 | 出问题可一键停 |

## 7. 与声纹 / 说话人的联动

热词里的**人名**与声纹库是同一批实体，应该双向打通：

| 场景 | 行为 |
|---|---|
| 登记人名热词 | 勾选"同时注册声纹"→ 跳到登记向导（见 [04 文档 §7](04-重叠说话与声纹登记设计.md)） |
| 声纹库新建人物 | 自动写入一条 `type=person` 的热词 |
| 说话人改名为新名字 | 自动补一条热词（下次直接识别） |
| 删除人物 | 询问是否一并删除热词（默认保留，仅停用） |

> 收益：注册 5 个同事，不仅说话人能认名，逐字稿里提到他们名字的地方也不会再写错——两份投入、两处收益。

## 8. 与 Obsidian 的联动

- `type=person` 的热词 → 生成/维护 `人物/<姓名>.md`（含 `aliases` frontmatter）；
- `type=project` 的热词 → 笔记中的 `[[项目/xxx]]` 双链与 `项目/` 标签；
- 笔记 frontmatter 增加 `hotwords_used: 5`，便于回溯"这篇用到了哪些热词"。

## 9. 度量与治理

| 指标 | 目标 | 采集 |
|---|---|---|
| 热词命中率（登记词在语音中出现的比例） | ≥ 80% | `hotword_stats` / 全文匹配 |
| L2 修正准确率（修正后用户未撤销） | ≥ 95% | `reverted` 字段 |
| 误报率（被撤销 / 总修正） | ≤ 5% | 同上 |
| 从未命中的条目占比 | ≤ 30% | 定期清理建议 |
| 热词带来的耗时增量 | ≤ 3% | 前后 RTF 对比 |

**治理动作**：从未命中 → 提示"可能登记错了/没出现过"；误报高 → 自动降权并提示补充别名。

## 10. 风险

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| R1 | 过度替换（把正常词换成热词） | 文本失真 | 阈值 + 最小长度 + 误报统计 + 一键撤销 |
| R2 | 同名不同人（两个"豆豆"） | 张冠李戴 | `scope` 按项目隔离 + 权重裁决 + 冲突报错 |
| R3 | 热词过多稀释 L1 偏置 | 效果反而变差 | 上限 50 + 按权重截断 + A/B 验证 |
| R4 | 多音字拼音错误 | 模糊匹配失效 | 允许手工覆盖 `pinyin` |
| R5 | 隐私（人名/宠物名属个人信息） | 合规 | 仅本地存储，导出可选脱敏 |
| R6 | LLM 把已修正的词改回去 | 前功尽弃 | L2 在 LLM 之后**再跑一遍**（幂等） |

## 12. 验收标准

- **AC-H1**：登记 `沈知微 / 河坊街` 后重跑测试音频，输出为 `沈知微`、`河坊街`（当前 4/6 → 6/6）。
- **AC-H2**：只登记标准写法、不填别名，同音错字（`沈志威`）也必须被修正（靠拼音模糊）。
- **AC-H3**：登记 50 条热词后，处理 1 小时音频的耗时增量 ≤3%。
- **AC-H4**：同一别名映射到两个不同热词时，必须报冲突并阻止保存。
- **AC-H5**：`/hotwords` 的"试一段"能并排显示加/不加热词的差异，并标出每处修正。
- **AC-H6**：撤销某处 L2 修正后，该条的误报计数 +1；误报率 >10% 的条目自动标警告。
