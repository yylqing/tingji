## 0. 三个直接回答

### Q1：说话人 1 和说话人 2 同时说话，能区分吗？

**当前方案不能。** 不是"调参能解决"的那种不能，是**信息层面做不到**：

> 两个人同时发声 → 声波在空气里就已经相加成一个信号 → 单麦克风录音里**没有**"这是谁的成分"这种信息。
> 任何方案要区分，都必须先做**分离**（用声纹、空间信息或模型先验把混合信号拆开），而分离质量目前达不到"直接出稿"的水平。

本机实测（23.06s，两段真实重叠，见 §1.3）：

| 真值 | 系统输出 |
|---|---|
| 4.1–11.9s 张三说"第一是第四季度的交付节奏…第三是下个月的招聘计划" + 李四同时说"那这样，交付这块你出一个风险清单…" | `[4.13–8.11] S1: 第一是那这一季度的交付结在你出一个风险清单，` |
| | **两个人的词被缝成一句，且整体归给了一个人** |

**能做的**（这也是本设计的主张）：**检测到"这里有多人同时说话"，标注出来，不硬猜归属**。这比给一个错误答案有价值得多。

### Q2：声纹登记用什么句子？

设计了 **3 句、129 字、约 31 秒**的登记文本，量化验证音素覆盖：**声母 21/21、韵母 35/36、声调 5/5，综合覆盖率 99.1%**（仅缺 `ueng`，只有"翁"这一个音节）。另配 1 段自由说话。

### Q3：Web 上怎么登记？

三步向导：**填信息 → 跟读（提词器 + 实时质检）→ 质检报告 + 入库**，并支持"从已有任务的说话人一键登记"（声学条件最匹配，推荐路径）。详见 §7。

## 1. 重叠说话：问题与实测

### 1.1 三种重叠形态（处理策略不同）

| 形态 | 例子 | 对转写的影响 | 策略 |
|---|---|---|---|
| **A 附和式**（backchannel） | 一方在说，另一方插"嗯/对/是的" | 插话词被吞或粘到主说话人句子里 | 丢弃或标注，不进正文 |
| **B 部分重叠** | 抢话，两人各说各的 2–4 秒 | 串词、乱码、归属错误 | **检测 + 标注** |
| **C 完全重叠** | 多人同时争论 | 整段不可用 | 标注 + 提示人工复核 |

A 类占实际会议的大多数，代价小；B/C 类是本次要解决的问题。

### 1.2 测试怎么构造的

用两段 TTS 中文语音做**时间轴叠加**（非拼接）：

- 轨道 A：张三（TTS-Tingting）0–11.6s + 李四（TTS-Meijia）12–23s
- 轨道 B：李四 4–15s
- 重叠区间：**4.1–11.6s（张+李，均衡）**、12–15s（李四与自己的另一段，作对照）
- 总长 23.06s

> 局限：合成音、无噪声、无房间混响；两人音量相等（0dB）。真实会议中音量差通常 3–10dB，比这个更"好处理"。

### 1.3 实测结果

**均衡重叠（0dB）下 FunASR 全链路输出**：

```
[ 0.05– 0.87] S0: 各位同事，
[ 1.15– 3.85] S0: 我们今天的周会主要讨论三件事。
[ 4.13– 8.11] S1: 第一是那这一季度的交付结在你出一个风险清单，     ← 串词
[ 8.47–11.87] S1: 周五之前给我数据切的就先做灰度。               ← 串词
[11.99–14.91] S1: 我先说一下前我下的问题跟人事对齐，               ← 串词
[14.91–16.87] S2: 我们有两个模块的进度，                        ← 重叠结束后恢复正常
```

特征很清楚：

1. **串词**：`第一是那这一季度的交付结` = 张的"第一是第四季度的交付节奏" + 李的"你出一个风险清单"的碎片缝合；`前我下的问题` = "我先说一下交付的问题" + "我下周跟人事对齐"。
2. **整句归属单一说话人**（S1），另一人完全消失。
3. **重叠一结束（14.9s）立刻恢复正常**——说明问题只发生在重叠区间。
4. 说话人数量仍被识别为 3 个（S0/S1/S2），但 **S1 实际是"张三+李四"的混合体**。

**一方明显占优（干扰低 10dB）时**：ASR 输出**完全正确**，干扰被当噪声忽略。

> 这带来一个关键产品判断：**只有当两人音量接近时，重叠才会毁掉转写**。而这时恰恰也是分离最难的。

### 1.4 为什么会这样（机理）

```
单人语音 → ASR 编码器 → 文本      ✅
混合语音 → ASR 编码器 → 试图解码成"一段连续的话" → 把两句话缝成一句
         ↘ 段级 CAM++ 取的是整段的"平均音色" → 落在两个人中间 → 聚到谁那边都"像"，随机
```

三个环节同时失效：

- **VAD** 只按能量切句子，不知道有几个人；
- **ASR** 是"单声道单说话人"假设训练出来的，没有"多标签"输出；
- **聚类** 用的是段级平均 embedding，混合段的向量是两人的加权平均，**不是任何一个人**。

### 1.5 试过目标说话人提取（VoxLock），不够用

sherpa-onnx 2.0.1 提供 VoxLock（目标说话人提取：给一段该人语音样本，保留他、压制其他人）。实测：

| 场景 | 处理 | 结果 |
|---|---|---|
| 官方中文样例（32.5s 双人混合） | 提取女声 | 文本比原混合更干净（重复词减少），**但仍有另一方内容** |
| 本机重叠样本（0dB） | 提取张三 | 仍出现李四的"拟出一个风险平台"；且新增错误（"救习计划"） |
| 本机重叠样本（0dB） | 提取李四 | 仍出现张三的"各位同事，我们今天的周会…" |
| 一方主导（-10dB） | 提取张三 | 不需要——ASR 本来就没被干扰 |

性能数据（本机实测）：32.5s 音频 5.56s（5.8× 实时），峰值内存 388MB，模型 69MB(int8)/90MB(fp32)。
规格（官方）：27M 参数、causal band-split RNN、注册样本 ≥3s、Apache-2.0、CPU 单线程、算法延迟 24ms；AMI 英语真实会议 WER 10.12%。

**为什么中文效果差**：VoxLock 训练集是 LibriSpeech + AMI（**英语**），官方**没有中文评测**；模型定位是"1 个目标 + 背景人声"，并非"两路对等分离"。

**结论**：VoxLock 是"目标增强/压制"，不是"硬分离"。可以做**人工点选的辅助工具**，不能做自动出稿的默认环节。

### 1.5b 改试 MOSS-Transcribe-Diarize：内容能分开，时间轴不行

后续调研发现更合适的方案：端到端音频大模型 **MOSS-Transcribe-Diarize 0.9B**（Apache-2.0）用自回归方式**同时生成文本与说话人标签**，不是聚类。同一段重叠音频实测：

```
[0.07][S01]各位同事…第三是下个月的招聘计划。[11.81]          ← 只有张三
[3.98][S02]好，那这样，交付这块…数据迁移就先做灰度…[23.03]    ← 只有李四
[12.12][S02]招聘的事情我下周跟人事对齐。[14.95]
```

| 维度 | 判定 |
|---|---|
| 内容分离 | ✅ 两人各自完整，**没有串词**（FunASR 是缝成一句乱码） |
| 说话人归属 | ✅ 正确 |
| **时间戳** | ❌ 乱序（`[11.81]` 后接 `[3.98]`），区间互相重叠，**不可直接用** |

**所以 1.5 的 VoxLock 方案被它替代**：同样解决重叠，MOSS 效果更好、只需一次推理（VoxLock 要每个说话人各跑一次）、且同一模型还能顺带修正专名（热词实测把 `ClickHouse/联调/双写` 全部改对）。

代价是速度：CPU 上约 1.5–2× 实时（FunASR 21×）。因此只在**重叠窗口**上按需调用，而不是全量跑。

详见[专项调研](../docs/research/moss-transcribe-diarize.md)。

### 1.6 能力边界（写清楚，避免过度承诺）

| 能力 | 现状 | 说明 |
|---|---|---|
| 单人轮流发言的分离与认名 | ✅ 可用 | 实测 21× 实时 |
| 检测"这里有多人同时说话" | ✅ 可做（§3 已验证） | 段内嵌入一致性 |
| 一句话里两人同时说，切成两句分别归属 | ❌ 做不到 | 需要真正的语音分离 |
| 分离后分别转写、自动合并回时间轴 | ⚠️ 实验性 | VoxLock 实测不干净，只能人工复核 |
| 附和词（"嗯/对"）识别与归属 | ⚠️ 部分 | 默认丢弃，不计入正文 |

> **业界现状（有来源）**：Otter 官方帮助页明确要求"避免重叠说话"，说明同时说话时无法判断归属，只能由用户手动修改 speaker label，**不做分离**；通义听悟只提供"2 人/多人"分离开关，未承诺重叠分离。飞书妙记、腾讯会议、Teams 未见公开说明（未确认）。
> 可见"检测 + 标注 + 人工复核"是当前主流工程折中，不是本方案的偷懒。

## 2. 方案设计（三级能力，逐级开启）

| 级别 | 能力 | 成本 | 可靠性 | 优先级 | 默认 |
|---|---|---|---|---|---|
| **L1** | 检测重叠区间 + 标注 + 不硬猜归属 | 极低（复用已有 embedding） | 中高 | **P0** | 开 |
| **L2** | 时间轴可视化重叠带 + 候选说话人并列 | 低（前端） | 高 | P1 | 开 |
| **L3** | 重叠窗口 → **MOSS 重转写**（内容可分开，时间需重映射） | 中（模型 1.82GB + 1.5–2× 实时，按重叠时长计费） | 中（内容可信，时间不可信） | **P1** | 关（手动触发） |

**L1 是本期唯一的硬要求**，L2 是展示层，L3 是"手动触发的增强"（默认关，UI 明示"内容更准，但时间轴为估算"）。

## 3. L1 检测算法（可直接实现）

### 3.1 主信号：段内嵌入自一致性

**思路**：一段真人单说话人语音，切成 1 秒小窗，各窗的声纹向量应该高度相似；如果这段是两人混合，各窗的"谁占主导"会随音量起伏变化，向量一致性显著下降。

实测（1 秒窗、0.5 秒跳，CAM++，段内两两余弦均值）：

| 数据 | 一致性范围 | 均值 | 判定 |
|---|---|---|---|
| 无重叠基线（19 段，14 段可计算） | **0.657 – 0.872** | 0.764 | 全部正常 |
| 重叠音频中的**混合段**（3 段） | **0.554 / 0.567 / 0.626** | 0.582 | 全部命中 |
| 重叠音频中的**非混合段**（4 段） | 0.773 – 0.875 | 0.826 | 未误报 |

在这 22 个片段上，用阈值 **0.62** 可**完全分开**（0 漏报 0 误报）。基线最低 0.657，混合段最高 0.626，间隔仅 0.031——**样本太小，不能当作精确阈值**，但信号方向是确定的。

**实现**：

```python
def overlap_score(clip, sr, extractor, win_sec=1.0, hop_sec=0.5):
    """返回段内嵌入一致性 [0,1]；段太短返回 None。"""
    win, hop = int(win_sec * sr), int(hop_sec * sr)
    if len(clip) < win + hop:
        return None
    embs = []
    for i in range(0, len(clip) - win + 1, hop):
        e = extractor.embed(clip[i:i + win])
        if e is not None:
            embs.append(e)
    if len(embs) < 2:
        return None
    return mean_pairwise_cosine(embs)
```

### 3.2 辅信号

| 信号 | 计算 | 作用 |
|---|---|---|
| 聚类边距 `margin = sim1 − sim2` | 段向量与各簇质心的第一名、第二名之差 | **全局**判断这段录音是否含重叠（混合会污染质心，导致整体边距下降：实测重叠文件边距 0.096–0.137，基线 0.253–0.702） |
| 段级 `sim1` 偏低 | 与最优簇相似度 < 0.62 | 单段可疑 |
| 短段（<2s）无法计算一致性 | — | 用 margin 兜底，或标记 `unknown` |

**已排除的信号**：字/秒（语速）。直觉上混合段会更密，但实测**反过来**——重叠时 ASR 是"丢词"而不是"混词"，混合段 5.07 字/秒，基线 5.57 字/秒，无区分度。

### 3.3 决策规则

```
for seg in segments:
    if seg.duration < 2.0: 
        seg.overlap = "unknown"
    else:
        c = overlap_score(seg.audio)
        m = seg.sim1 - seg.sim2
        if c is not None and c < 0.62:
            seg.overlap = "suspected"      # 强信号
        elif c is not None and c < 0.70 and m < 0.15:
            seg.overlap = "suspected"      # 弱信号 + 边距佐证
        else:
            seg.overlap = "none"
```

- 命中 `suspected` 的段：`speaker_id` 置空，`spk_candidates` 存 top-2 簇及分数，UI 显示"多人同时说话"。
- **不把可疑段放进簇质心计算**（见 3.4）。

### 3.4 顺带修一个 bug：用干净段重算质心

混合段会污染簇质心（实测：重叠文件的质心互相靠拢，使所有段的 margin 都掉到 0.1 左右）。因此：

> **第一轮**：用全部段聚类 → 算一致性 → 剔除可疑段
> **第二轮**：用剩余干净段重算质心 → 重新比对 → 认名

这一步能同时提升**重叠检测**与**声纹认名**的准确率，几乎零成本。

### 3.5 为什么本期不用帧级 OSD（有更好的，但不划算）

调研确认了两条可行但本期不采用的路线：

| 路线 | 事实 | 为什么不用 |
|---|---|---|
| **pyannote OSD**（`pyannote/overlapped-speech-detection`） | 独立重叠检测管道，MIT 代码、AMI/DIHARD/VoxConverse 训练 | 模型权重 **gated**（需 HF token + 接受条款），与本项目"克隆即用、离线可跑"的前提冲突；可作为可选插件 |
| **sherpa-onnx segmentation-3.0 的 powerset** | 3 个 speaker slot、每帧最多 2 人、7 类组合，理论上能表达重叠 | 提取 embedding 时 `ExcludeOverlap` 会**丢弃重叠帧**，CLI 也不输出 overlap 标志；要拿到帧级人数需要自己改 C++/读中间输出，工程量与收益不匹配（模型仅 5.7MB，但接入成本高） |

结论：**本期用嵌入一致性（纯 Python、零新依赖、复用已有 CAM++）**，把帧级 OSD 列为 P1 增强，等真实数据证明一致性法漏检率过高再上。

### 3.6 局限（必须写在文档里）

- 只在"两人音量接近"时有效；一方主导时检测不到，但那时也不需要（ASR 本来就正确）。
- 对**同一人重复说话**（如"我我我觉得"）可能误判为低一致性 → 需结合 duration 与文本。
- 阈值 0.62 / 0.70 来自 22 个合成片段，**必须在真实会议数据上重新校准**（见 §8 验收）。

## 4. 产品行为规范

### 4.1 逐字稿怎么显示

```
**李四** `[00:03:21]`
目前我们有两个模块的进度落后了大概一周，主要是接口联调卡住了。

**多人同时说话** ⚠️ `[00:04:07 · 4.1s]`  （可能是：张三 / 李四）
> 第一是那这一季度的交付结在你出一个风险清单，
> 识别内容可能不完整或串词，建议回听音频。

**张三** `[00:04:16]`
第三是下个月的招聘计划。
```

要点：
- 用醒目的"多人同时说话"标签替代臆测的人名；
- 正文**保留** ASR 原文（不删），并加"可能串词"提示；
- 提供 top-2 候选（不是断言）；
- 点击可直接播放该区间。

### 4.2 归属决策原则

| 情况 | 决策 |
|---|---|
| 一致性正常 | 按聚类结果归属 |
| 可疑 + top1 相似度 ≥0.75 且领先 ≥0.10 | 归给 top1，但保留"⚠️ 可能重叠" |
| 可疑 + 无明确优势 | **不归属**，显示"多人同时说话" |
| 用户手动指定 | 以用户为准，回写声纹库 |

一句话：**宁可显示"不知道"，也不要显示一个错的人名**——错人名比空着更有害（会把决议记到错误的负责人头上）。

### 4.3 用户可做的操作

| 操作 | 说明 |
|---|---|
| 回听 | 点标签跳转到该区间 |
| 指定说话人 | 三选一：A / B / 两人都说（选"两人都说"则保留为重叠） |
| **重转写此段** | 调用 L3：截 ±3s 窗口送 MOSS，取其文本与说话人，时间按 VAD/FunASR 边界重映射，结果并列展示 |
| 拆分 | 手工把该段文本拆给两个人（编辑归属） |
| 忽略 | 标记为 `ignored`，不进导出 |

### 4.4 导出与 Obsidian

- Markdown / TXT：`[多人同时说话]` 前缀 + 原文
- SRT：该条 `content` 前置 `[重叠]`
- frontmatter 增加 `overlap_count: 3`，便于筛选

## 5. 数据模型与配置变更

```sql
ALTER TABLE segments ADD COLUMN overlap_flag TEXT;      -- none|suspected|unknown|confirmed
ALTER TABLE segments ADD COLUMN overlap_score REAL;     -- 段内一致性
ALTER TABLE segments ADD COLUMN spk_candidates TEXT;    -- JSON [{cluster, score}]

CREATE TABLE overlap_events (
  job_id TEXT, start_ms INTEGER, end_ms INTEGER,
  candidates TEXT,          -- JSON
  score REAL,
  method TEXT,              -- embedding_consistency|margin|manual
  resolved_by TEXT,         -- auto|user
  PRIMARY KEY (job_id, start_ms)
);
```

```yaml
diarization:
  overlap_detect: true
  overlap_consistency_threshold: 0.62   # 需真实数据校准
  overlap_margin_threshold: 0.15
  overlap_min_duration_sec: 2.0
  centroid_refine: true                 # 剔除可疑段后重算质心

overlap_repass:        # L3，默认关
  enabled: false
  engine: moss         # moss | voxlock(备选,已不推荐)
  model_dir: models/moss
  window_pad_sec: 3.0  # 前后各留 3 秒，避免切断句子
  remap_timestamps: true   # 用 VAD/FunASR 边界重映射 MOSS 的时间
  trigger: manual      # manual | on_overlap_confirm
```

## 6. 声纹登记设计

### 6.1 四条设计原则

1. **文本无关 embedding（text-independent）**：CAM++ 不需要固定口令，所以文本的作用是**覆盖音素**，而不是"密码"。
2. **声学条件匹配优于时长**：用会议同款麦克风、同距离录 20 秒，比贴着嘴用耳麦录 60 秒更有效。
3. **多向量优于单向量**：同一人 2–3 段（不同日期/设备）存多个向量，匹配取最大值。
4. **宁可要用户多读 10 秒，也不要一个质量差的模板**——坏模板会长期污染认名。

### 6.2 登记文本（3 句 + 1 段自由说）

**标准模式：3 句，129 字，约 31 秒（自然语速 4.2 字/秒）**

| # | 文本 | 汉字 | 时长 | 设计意图 |
|---|---|---|---|---|
| S1 | 今天下午三点半，我们在地铁站旁边的小楼里核对预算表，讨论会议内容和交付节奏。 | 35 | ≈8.3s | 数字/时间 + 平翘舌（四/站）+ n-l（楼/里）+ 鼻音收尾 |
| S2 | 这个季度的目标是把接口响应时间从三百毫秒降到一百二十毫秒，同时保证 API 的稳定性，减少数据波动。 | 42 | ≈10.0s | 数字密度 + 英文术语 + 前后鼻音（响/应/间/定）+ 双唇音（百/波） |
| S3 | 如果需要的话，我可以把详细的流程图快速发到群里，大家再决定这一类问题要不要全部采用，顺便跟兄弟部门确认一下情况。 | 52 | ≈12.4s | ü 系列（需/群/决/全）+ uai（快）+ ei（类）+ r 声母（任务/确认）+ iong（兄弟）+ uang（情况） |

**自由说话（可选，建议做）**：15–20 秒，说说"最近在做的一件工作"。作用：捕捉**自然语调与语速**，纠正"朗读腔"与真实说话的声学差异。

**为什么不用一句话搞定**：太短（<10s）的模板方差不稳定；且音素覆盖不足会让某些音节上的区分力变弱。

### 6.3 音素覆盖怎么验证的（可复现）

脚本 `bench/phoneme_coverage.py`，用 `pypinyin` 逐字取声母/韵母/声调，与普通话标准集比对（含 `iu/ui/un` 还原为 `iou/uei/uen`）：

```
句数=3  汉字数=129  预估朗读时长≈30.7s
声母 21/21   缺: 无
韵母 35/36   缺: ueng
声调 5/5      缺: 无
综合覆盖率 = 99.1%
```

唯一缺口 `ueng` 只有"翁/wēng"这一个音节（零声母），日常会议几乎不出现，**不值得为它加一句**。

### 6.4 采集规范

| 项 | 要求 | 原因 |
|---|---|---|
| 环境 | 安静房间，背景噪声越低越好 | 噪声会进入模板 |
| 设备 | **用你开会时用的那个麦克风**（内置麦或会议麦） | 声学条件匹配比音质更重要 |
| 距离 | 20–40cm，正对麦克风（无公开硬标准；太近有近讲效应与喷麦，太远混响重） | 声学条件匹配 |
| 语速 | 自然，别刻意放慢或播音腔 | 与会议真实语速一致 |
| 音量 | 正常说话音量，波形峰值 −12 ~ −6 dBFS | 避免削波 |
| 次数 | 至少 1 次完整 3 句；建议隔天再录 1 次（共 2 个模板） | 跨会话鲁棒性 |
| 禁忌 | 不要多人一起读、不要边说边笑、不要用变声/降噪软件 | 污染模板 |

### 6.5 质检门控（6 项，全部通过才入库）

| # | 指标 | 阈值（默认） | 不通过时 |
|---|---|---|---|
| 1 | 有效语音时长 | 20–60s | 提示"太短/太长"，重录 |
| 2 | 语音占比 | ≥ 60% | 提示"静音太多，检查麦克风" |
| 3 | 估计 SNR | ≥ 15 dB | 提示"换安静环境" |
| 4 | 削波比例 | < 0.1% | 提示"音量过大，调低增益" |
| 5 | 单说话人校验 | 跑一次分离，检出人数必须 = 1 | 提示"检测到多人声音，请单独录制" |
| 6 | 句间自一致性 | 三句向量两两余弦 ≥ 0.70 | 提示"三句差异过大，可能有插话或环境变化" |

> 全部为**工程默认值**，需用 10 人 × 2 次真实录音标定（见 §8）。
> 参考：Azure 文本无关注册下限为有效语音 20s / SNR 2dB（接口下限，工程上远不够）；腾讯云 `QualityCheck` 会检查多说话人、SNR、截幅；PCAC 0010-2021 要求 16k/16bit 并做截幅、SNR、完整性质检。我们把 SNR 门槛提到 15dB、削波限到 0.1%，均严于公开下限。
> 第 5 项是很多人忽略但很关键的一步——用同一套分离器自检，能挡住"两人一起念"和"背景有人说话"。

### 6.6 入库策略

- 每个会话产出 **3 个句向量 + 1 个 L2 归一化质心**，全部入 `voiceprints`（带 `session_id`、设备标签、质量分）。
- **匹配策略分级**（这是与主流做法对齐的关键）：
  - **同条件**（同设备/同环境）：用质心比对——L2 归一化后取均值是最常用、最稳的聚合方式；
  - **跨条件**（换设备/换房间）：用**逐向量取最大值**（max fusion），避免均值被条件差异冲淡。
  - 实现上两者都算，取较高分，并在 UI 显示"命中来源（质心/单样本）"。
- 不建议用"单条最近邻"作为唯一依据（对噪声敏感）。
- 上限：每人物 ≤ 6 个会话（超出保留质量分最高的 6 个）。

> 依据：NIST SRE24 允许单段 10/30/60s 或三段注册；Azure 文本无关注册要求有效语音 ≥20s（上限 300s）；T/PCAC 0010-2021 要求 16k/16bit。本设计取 **16k/单声道/≥20s** 作为下限，推荐 ~30s。

### 6.7 防重复注册 / 防误认

| 检查 | 条件 | 行为 |
|---|---|---|
| 已注册他人 | 新模板与库中**其他人** top1 ≥ 0.80 | 弹窗："声纹与『张三』高度相似（0.83），是否合并或确认是同一人？" |
| 已注册本人 | 与**本人**已有模板 < 0.50 | 提示："与历史样本差异较大，是否换了设备/正在感冒？" |
| 注册数溢出 | 同一人 ≥ 6 个会话 | 提示清理 |
| 认名阈值 | top1 ≥ 0.72 且领先 ≥ 0.05 | 自动命名；否则待确认 |

### 7.2 三步向导

**Step 1｜基本信息**

```

备注    [                ]     （可选）
☑ 同时在 Obsidian 创建人物笔记 [[人物/李四]]
```

**Step 2｜跟读**

```
┌──────────────────────────────────────────────────────────┐
│  请用自然语速朗读下面这句（第 1 / 3 句）                     │
│                                                          │
│      今天下午三点半，我们在地铁站旁边的小楼里核对预算表，      │
│      讨论会议内容和交付节奏。                                │
│                                                          │
│  ▁▃▅▇▅▃▁▂▄▆▄▂  ← 实时波形                                │
│  ▮▮▮▮▮▮▮▮▮▮▮▮▮▮▮▮▮▮▯▯▯  00:08 / 00:31   ● 录音中         │
│  [重录本句]  [跳过]  [改为上传文件]                         │
└──────────────────────────────────────────────────────────┘
```

交互细节：

- **大字提词器**（≥28px，行高 1.8），一屏一句，避免读者低头看稿；
- 每句结束由 **VAD 自动检测 1.2s 静音**自动切下一句，也允许手动点"下一句"；
- 进度条按"已完成句数"推进，不按时间（避免用户抢读）；
- 逐句独立校验，**某句不合格只重录该句**，不用全部重来；
- 麦克风电平条 + 实时提示（"声音太小"/"有削波"）；
- 全程可暂停；刷新页面会保留已完成句子（session 恢复）；
- 首句前有 3 秒"请开始"倒计时，避免开头被吞。

**Step 3｜质检与入库**

```
┌──────────────────────────────────────────────────────────┐
│  ✅ 质检通过                                              │
│                                                          │
│  有效语音  27.4s      语音占比  82%      SNR  ≈ 24 dB     │
│  削波      0.0%       单说话人  ✅        句间一致性 0.81  │
│                                                          │
│  与库中其他人最高相似度：0.31（李四）—— 无重复             │
│                                                          │
│  [试听]   [重录]   [保存声纹]                             │
└──────────────────────────────────────────────────────────┘
```

不合格时逐项给出**具体动作**（不是"失败"两个字）：

```
⚠️ 3 项未通过
  语音占比 48%（要求 ≥60%）→ 环境太安静？麦克风可能没收到声音，请重录。
  单说话人 ❌ 检测到 2 人 → 请确认房间里只有你一个人。
  句间一致性 0.62（要求 ≥0.70）→ 第 2 句与其它两句差异较大，建议重录第 2 句。
```

### 7.3 从任务登记（推荐路径）

任务详情页，每个说话人标签后有"这是谁？"：

```
● 说话人2  00:11:12   [这是谁？▾]
                          ├ 张三（相似度 0.63，建议确认）
                          ├ 李四
                          ├ 新建人物…
                          └ 不是一个人（拆分）
```

选择后：
1. 把该簇的**音频拼接段（≤60s）**直接作为登记样本（跳过朗读步骤）；
2. 自动计算质检指标，展示"是否入库"；
3. 若命中"新建人物"→ 只需填姓名，一键入库；
4. 入库后**立即重算**本任务其余说话人的匹配结果。

> 这是实践中命中率最高的一条路——用户本来就要改一次名，顺便就完成了注册。

## 8. 验收标准

**重叠（L1）**

- AC-O1：给定本仓库的重叠测试音频，系统标出 4.1–11.9s 为"多人同时说话"，**且不把该段归给任何单一说话人**。
- AC-O2：同一说话人的连续独白（无重叠）不得被误标（基线 19 段误报 = 0）。
- AC-O3：真实会议基准集（≥10 段）上，重叠区间**检出率 ≥ 70%**、**误报率 ≤ 10%**，阈值据此重新标定。
- AC-O4：重叠段在 Obsidian 笔记中以 `[多人同时说话]` 标记，导出 SRT 带 `[重叠]` 前缀。

**声纹登记**

- AC-V1：按向导朗读 3 句（≥20s）后，质检 6 项全部展示，通过后 3 秒内入库。
- AC-V2：用同一人的另一段录音测试，认名相似度 ≥0.72（真实数据上统计，10 人规模）。
- AC-V3：故意两人一起朗读，第 5 项（单说话人）必须拦截。
- AC-V4：把已有人员的录音再注册一次，必须弹出"疑似重复"警告。
- AC-V5：从任务详情登记一个人，全篇该说话人立即改名，且 Obsidian 链接同步更新。

## 9. 风险与待定

| # | 项 | 说明 | 下一步 |
|---|---|---|---|
| R1 | 重叠阈值未在真实数据校准 | 0.62/0.70 来自 22 个合成片段 | M2 前用真实会议标定 |
| R2 | 附和词（"嗯/对"）归属 | 目前直接丢弃，可能丢失"有人附和"这一信息 | P2 评估是否单独记录 |
| R3 | 重叠重转写的时间轴 | MOSS 在重叠段输出乱序时间戳 | 只用其文本，时间由 VAD/FunASR 重映射；UI 标注"时间为估算" |
| R3b | MOSS 速度 | CPU 约 1.5–2× 实时，全量跑 1 小时约需 30 分钟 | 只对重叠窗口按需调用（占比 <10%，预计 +2 分钟/小时） |
| R4 | 登记文本的用户接受度 | 129 字朗读对部分人是负担 | 提供"快速模式"（仅 S1+S2，约 18s，覆盖 88%） |
| R5 | 声纹老化 | 感冒/换设备会降分 | 每次确认后自动累积新模板 |
| R6 | 隐私 | 声纹是生物特征 | 本地存储、加密可选、支持一键删除 |

**待定问题**

1. 是否接受"快速模式"（18s，覆盖 88%）作为默认？——影响注册转化率。
2. 重叠段是否要在笔记里保留原文？——保留更透明，但读者会看到乱码。
3. 是否允许"两人都说"这种归属？——语义上更真实，但下游（待办归属）无法处理。

## 附录：Web 多段登记的落地（v0.12.0）

页面 `/voices` 把本文 §6.2 的 3 句 + 1 段自由说话直接列出来，每段可现场录制或上传文件：

1. 每段独立 `MediaRecorder` 录音 → 本地预览 → 可重录；
2. 一次提交全部段落（`files` 多文件上传，兼容单文件）；
3. 服务端逐段校验（<1.5s 拒绝）、提向量、入库；
4. 计算**三句自一致性**（两两余弦均值），低于 0.70 提示可能有插话/环境变化；
5. 认名时同一人多条样本按人取最大相似度，再比较领先幅度（避免自己比自己）。

这样既满足 §6.4 的"3 句 + 自由说"要求，也避免了"录完 3 段无法一次上传"的体验问题。
