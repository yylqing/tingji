## 0. 一句话

**它做的是"实时预览"，我们做的是"离线精修"——两者不是竞争关系，而是同一条产品链的两端。**
它有几个可以直接抄的小工程点（幻觉黑名单、静音门控、参数取舍），但它的核心缺陷（3 秒硬切、无重叠、时间戳是墙钟）
恰好是我们**不该犯**的错。

---

## 1. 它的技术路线

```
浏览器/本地麦克风
   ↓ sounddevice，BLOCK_SIZE=2000 样本（16k 下 0.125s）
队列 ──► 缓冲 3 秒（BUFFER_SECONDS=3）
          ↓ 预处理：归一化 + 差分高通
          ↓ 静音门控：能量 + 过零率 + 频谱质心
          ↓ faster-whisper large-v3-turbo（CPU int8，8 线程）
          ↓ 质量过滤：exp(avg_logprob) ≥ 0.5、幻觉黑名单、重复、纯标点
          ↓ WebSocket 广播（带"墙钟时间戳"）
浏览器逐段追加显示（不落库、不导出、无说话人）
```

关键参数（`app/config.py`）：

| 项 | 值 | 意图 |
|---|---|---|
| `BLOCK_SIZE` | 2000 样本 | 降低采集块延迟（注释：从 4000 减半） |
| `BUFFER_SECONDS` | **3** | "最大的延迟优化"（注释原文） |
| `DEFAULT_MODEL` | `large-v3-turbo` | 精度接近 large，速度接近 tiny |
| 推理 | `beam_size=1`、`best_of=1`、`condition_on_previous_text=False`、`word_timestamps=False` | 全部为速度让步 |
| VAD | `vad_filter=True`，`min_silence_duration_ms=500`、`speech_pad_ms=400` | 过滤无效推理 |
| 反幻觉 | `no_speech_threshold=0.6`、`compression_ratio_threshold=2.4`、`log_prob_threshold=-1.0` | Whisper 官方三件套 |
| 语种 | `language="zh"` 固定 | 中文场景 |

## 2. 它真正值得抄的三点

### 2.1 幻觉黑名单（我们已落地）

Whisper 在静音/音乐上会稳定输出固定套话，它列了 15 条正则：

```python
r"优优独播剧场", r"请不吝点赞", r"订阅.*转发.*打赏", r"明镜与点点", r"感谢.{0,4}观看", ...
```

**我们采纳并扩展**：`app/hallucination.py`
- 黑名单 17 条（中英）+ 纯标点 + 空段；
- **不把"重复"当幻觉整段丢弃**——真口吃也是内容（我们用 `strip_repeats` 清理）；
- 在真实语料（6,853 段）上回放：只命中 **287 段纯标点段（4.2%）**，不误杀"嗯/是"这类真实应答。

> 这条是净收益：以前这些"。"段会进逐字稿和段落，占位置还可能干扰 LLM。

### 2.2 静音门控的三特征

它不只看能量，还结合**过零率 + 频谱质心**：

```python
is_silent = (energy < 0.01 and zcr < 0.15) or (energy < 0.015 and spectral_centroid < 100)
```

我们目前靠"字符率异常"事后判断（`quality_flag`），是**事后**的；它这个能**事前**跳过无效推理。
对批处理价值有限（我们本来就是整段送），但如果做实时模式，这是必备的省钱手段。

### 2.3 参数取舍的"实测注释"

代码注释里写着"从 4000 减到 2000""从 5 秒减到 3 秒""beam_size 从 5 降到 1"——**每次调参都留了前后对比**。
这种习惯值得学：我们的配置文件里也应该写"为什么是这个值"。

## 3. 它的四个硬伤（我们不要犯）

| 问题 | 后果 | 我们对应做法 |
|---|---|---|
| **3 秒硬切，无重叠** | 跨边界的词被切断/重复，`condition_on_previous_text=False` 让他**没有上下文**可用 | 我们用 VAD + 语义块 + 段落合并，并且**整段送模型** |
| **时间戳是墙钟**（转写那一刻的耗时） | 无法对齐音频、无法回听、无法纠错 | 我们的时间戳来自 ASR 模型，可回放、可校准 |
| **不落库、不导出、无说话人** | 只能看，不能用作纪要 | 我们整套 Obsidian/纪要/导出 |
| **`asyncio.run()` 在线程里调用** | 每个 chunk 新建事件循环，WebSocket 并发时会抖 | 我们用 FastAPI SSE，异步原生 |

## 4. 对我们最有价值的一条：**"实时预览 + 离线精修"双模**

它证明了一件事：**16k + 3 秒缓冲 + CPU int8 的 large-v3-turbo 可以做到 3 秒级延迟**。这意味着我们可以做：

```
录音中：浏览器分片 → WebSocket → 3s 块 ASR（SenseVoice，快）→ 实时字幕（预览，不保证准）
录音结束：完整音频走现有批量流水线 → 说话人分离 + 热词 + ITN + LLM 顺滑 + 纪要 → 最终稿
```

**价值**：
- 会议中能看见字幕（信任感），散会后 5 分钟拿到精修稿；
- 实时层不追求准确率，只求"看得见"；精修层负责质量；
- 现有 pipeline 完全不用改，只是新增一个入口。

**成本估算**：
- 前端：MediaRecorder 分片上传（已有录音组件，`/voices` 里写过）+ 一个 `/live` 页面；
- 后端：WebSocket 或 SSE + 3 秒块队列 + SenseVoice 单块推理（实测 SenseVoice 60s/0.9s，3s 块约 0.05s）；
- 录音结束把分片拼成完整文件， ingest 成普通 job（复用现有全部能力）；
- 工作量：**1.5–2 天**（含断线重连、分片落盘、进度显示）。

> 这是本次调研最有价值的结论：**实时不是替代批处理，而是批处理的"前菜"**。

## 5. 结论

| 维度 | 判断 |
|---|---|
| 技术路线 | 简单直接，适合"个人速记"，不适合"会议纪要" |
| 可借鉴 | 幻觉黑名单（已落地）、静音三特征（实时模式用）、调参留实测注释 |
| 不可借鉴 | 3 秒硬切、墙钟时间戳、无持久化 |
| 最大启发 | **实时预览层可以与现有批量流水线并存**，成本约 2 天 |

**产品决策（2025-10-31）**：**不做实时转写**。只采纳两个与实时无关的工程点——
幻觉过滤与静音门控，均已落地（见 [01 §3.17](../01-技术选型报告.md)、[02 FR-B5.2/FR-B2.2](../02-PRD.md)）。

> 保留本文档的实时方案分析，作为后续若要做实时预览时的成本参考（约 1.5–2 天）。
