# 调研 · 三个同类项目的技术实现与可借鉴点

> 对象：Meetily（32.3k★）、CapsWriter-Offline（7.0k★）、Brevia（75★）｜2026-10-31
> 方法：拉 README + 源码树 + 关键实现文件（ITN、热词、规则纠错），与我们的管线逐项对照。

---

## 0. 一句话结论

| 项目 | 它最强的地方 | 我们该抄什么 | 我们不该抄 |
|---|---|---|---|
| **Meetily** | Rust/Tauri 桌面端 + **系统声音捕获** + 多 LLM 供应商 | 系统声音（线上会议）采集；摘要模板化 | Rust 重写前端（成本高、收益低） |
| **CapsWriter-Offline** | **中文 ITN（含约数/成语保护）** + **正则规则纠错** + 音素热词 | ✅ 正则规则（已实现）、✅ ITN 约数（已实现）；音素匹配列为备选 | C/S + 全局热键（我们是转写，不是输入法） |
| **Brevia** | 手机录音→电脑转写 + **批量替换（带撤销）** + 悬浮字幕 | 批量查找替换的校对交互 | 实时字幕（用户已明确不做） |

## 1. Meetily（Zackriya-Solutions/meetily）

**技术栈**：Tauri（Rust 后端 + Next.js 前端），MIT，32k star，2026 年仍在高频更新。

**关键能力**
- **系统声音捕获**：macOS 用 CoreAudio/Metal、Windows 用 WASAPI，能直接录"电脑里播放的会议声音"（Zoom/Teams/腾讯会议），不需要外放。
- 实时转写：Parakeet（NVIDIA NeMo）/ Whisper，本地跑。
- 摘要：支持 Ollama / Claude / Groq / OpenRouter / 任意 OpenAI 兼容端点——**供应商可插拔**。
- 本地优先：数据不出机器。

**对我们的启发**
1. **系统声音采集**是最大缺口。我们现在只能"录完的文件"，线上会议要用户先录音再上传。
   在 macOS 上可以用 ScreenCaptureKit（macOS 13+）或 BlackHole 虚拟声卡把系统输出录成文件，
   然后**复用现有整条流水线**——不需要改 ASR/分离/整理任何一层。
2. **摘要模板**：Meetily 有多种 summary workflow。我们已有按类型的 prompt，
   可以再往前一步：每类内容一套模板（会议=决议/待办；访谈=观点；日常=时间线）。
3. 多供应商：我们只接 Ollama。加一个 `llm.provider`（openai-compatible）成本很低，
   收益是"没有本地大模型也能用"。

**不建议**：把 Web 改成 Tauri 桌面端——我们的形态是局域网 Web，改桌面端等于重做分发。

## 2. CapsWriter-Offline（HaujetZhao）

**技术栈**：Python + ONNX/GGUF，C/S 分离（服务端跑模型，客户端管热键/上屏）。

**它做得比我们深的四处**

### 2.1 中文 ITN 是"工程级"的

`core/tools/chinese_itn/` 拆成 `patterns.py`（总正则）、`mappings.py`（数字/单位映射）、
`ranges.py`（约数范围）、`replacer.py`、`resources/idioms.json`（**成语白名单**）。

- 约数：`三五百 → 300~500`、`十五六 → 15~16`、`三四 → 3~4`
- 成语保护：用 `idioms.json` 显式排除"三心二意""五花八门"这类
- 单位：`毫安时→mAh`、`赫兹→Hz`（这部分他们放在规则文件里）

**我们已采纳**：约数/范围（`app/itn.py`），实测
`十五六个人→15~16个人`、`三五百台服务器→300~500台服务器`、`二三十台机器→20~30台机器`、
`三四个问题→3~4个问题`，且 `二十三岁`、`三心二意` 不误伤。

**踩到的坑**（值得记）：范围转换必须**排在量词转换之前**——否则"三五百台"会先被当成 500。

### 2.2 正则规则纠错（hot-rule.txt）

```
毫安时     =      mAh
(艾特)\s*(\w+)\s*点\s*(\w+) = @\2.\4
欧拉玛   =  Ollama
```

热词表只能替换"词"，处理不了**结构化**的错（邮箱、网址、单位、反复出现的同音错字）。
规则文件是**用户可维护**的，比往代码里塞正则灵活得多。

**我们已采纳**：`app/rules.py` + `config/rules.txt`，8 条默认规则，实测
`邮箱是 艾特 zhangsan 点 com` → `邮箱是 @zhangsan.com`；坏规则只跳过不崩。

### 2.3 音素模糊匹配（备选）

他们用**音素**而非拼音做热词模糊匹配（`algo_phoneme.py`）。我们目前是拼音 + 编辑距离
（`rapidfuzz`），对南方口音（n/l、zh/z）已经够用；音素在"带调、连读"场景更准，但工程成本更高。
**结论：暂不换，列入观望。**

### 2.4 多引擎

Paraformer / SenseVoice / **Fun-ASR-Nano** / **Qwen3-ASR**，ONNX + GGUF，跑分：

| 模型 | 20s 音频 CPU 延迟 |
|---|---|
| Paraformer | 0.6s |
| SenseVoice-Small | 0.6s |
| Fun-ASR-Nano | 2.0s |
| Qwen3-ASR | — |

我们已支持前两个；Fun-ASR-Nano 如果能跑 ONNX，可以作为"更准但更慢"的第三选项。
**优先级低**：当前 Paraformer 在我们的真实会议数据上已经够用。

## 3. Brevia（zerolovesea）

**技术栈**：JS 桌面端 + 手机 App，ISC，75 star。

**关键能力**
- 手机录音 → 回电脑转写整理（"把会议室装进口袋"）
- **一次修正多处**：在逐字稿/笔记/纪要里预览、选择并**批量替换**，支持撤销；录音时还能把规则应用到**本场后续字幕**
- 悬浮胶囊：始终可见的录音状态 + 实时字幕
- AI 建议**逐条采纳**，不是一把梭

**对我们的启发**
1. **批量替换 + 撤销**是校对体验的关键。我们现在只能逐段改（`PATCH /segments/{idx}`），
   没有"全局查找替换"。这个功能对"某个名字全程识别错"的场景特别有用。
2. **规则应用到后续** = 我们的 `rules.txt` 已经是这个思路，但只在任务结束时跑一次；
   结合批量替换，可以让用户改一次、整篇生效。

**不建议**：悬浮字幕/实时转写（用户已明确不做）。

## 4. 采纳清单（按性价比排序）

| 优先级 | 事项 | 来自 | 成本 | 状态 |

| **P1** | **系统声音采集**（线上会议直接录） | Meetily/Brevia | 2–3 天 | 待定 |
| **P1** | 批量查找替换（带预览/撤销） | Brevia | 1 天 | 待定 |
| **P2** | 摘要模板按类型分（会议/访谈/日常） | Meetily | 0.5 天 | 待定 |
| **P2** | `llm.provider` 支持 OpenAI 兼容端点 | Meetily | 0.5 天 | 待定 |

→ 摘要模板（内容质量）→ 其余。

## 5. 一句话总结

三个项目分别代表三种取舍：**Meetily 抢"入口"**（系统声音、桌面端），
**CapsWriter 磨"文本质量"**（ITN、规则、音素），**Brevia 磨"校对体验"**（批量替换、悬浮）。

我们的定位是"本地会议转写 + Obsidian 归档"，**入口**和**校对体验**是当前短板，
**文本质量**已经领先（ILM 整理稿、类型判定、情绪、词级时间戳都是它们没有的）。
