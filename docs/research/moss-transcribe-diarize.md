# 调研 · MOSS-Transcribe-Diarize 0.9B 对本项目的价值

| 项 | 内容 |
|---|---|
| 调研日期 | 2026-10-30 |
| 本机环境 | Apple M4 / 16GB / macOS 26.5.2（transformers + torch CPU；MPS 亦测） |
| 结论 | **值得引入，但只作为"重叠区间二次转写"与"高质量模式"的可选项，不作为主引擎** |
| 一手来源 | [模型卡](https://huggingface.co/OpenMOSS-Team/MOSS-Transcribe-Diarize) · [GitHub README](https://github.com/OpenMOSS/MOSS-Transcribe-Diarize) · [arXiv 2601.01554](https://arxiv.org/abs/2601.01554) · [FunASR 部署指南](https://github.com/modelscope/FunASR/blob/main/docs/moss_transcribe_diarize_zh.md) |
| 实测脚本 | `bench/bench_moss.py`（结果见 `bench/result_moss_*.json`） |

---

## 0. TL;DR

**它解决的是我们最疼的两个问题**：中英混说专名错、重叠说话串词。

| 能力 | 我们现在的方案（FunASR） | MOSS 0.9B（本机实测） |
|---|---|---|
| 专名（ClickHouse） | ❌ 识别成"认批"/"标准查询" | ✅ **加热词后完全正确** |
| 同音词（迁移/双写/联调） | ❌ "交移"/"收息"/"连调" | ✅ **全部正确** |
| 重叠说话 | ❌ 两人词缝成乱码，整体归一人 | ✅ **内容能分开**（两人各自完整），但 ❌ **时间戳乱序** |
| 标点 | 外挂 CT-Punc，句级 | ✅ 原生，更自然 |
| 速度（本机 CPU） | ✅ **21× 实时** | ❌ **1.5–2× 实时**（慢约 10 倍） |
| 内存 | 4.35GB | 5.7GB |

**一句话**：质量明显更好，但用 transformers 在 CPU 上只有约 2× 实时（慢 10 倍）——**慢是运行时的问题，不是模型的问题**（GGUF+Metal 在 M4 Max 上标称 28–30× 实时，但本机 GitHub 不通，没能编译验证）。

**建议**：
1. **主引擎保持 FunASR**（速度不可替代）。
2. **重叠区间：改用 MOSS 窗口重转写**，替换掉原计划的 VoxLock 方案（实测 MOSS 明显更好）。
3. **高质量模式（P2）**：用户可对重要会议选 MOSS 全量转写，接受更慢。
4. **上 GGUF + Metal 做一次 PoC**，若在基础 M4 上能到 8× 以上，可考虑把它提为主引擎候选。

## 1. 模型是什么

| 项 | 值 |
|---|---|
| 发布方 | OpenMOSS / MOSI.AI（2026-07-09 开源） |
| 参数 | 0.9B：**Whisper-Medium 编码器**（24 层，d=1024）+ 4× 时间合并 + MLP 桥接 + **Qwen3-0.6B 因果解码器**（28 层） |
| 权重大小 | 1.82GB（bf16 safetensors，单文件） |
| 许可 | **Apache-2.0**（代码与权重） |
| 语言 | 50+；中文为重点（训练与评测以中文多人会议为主） |
| 输入 | 16kHz 单声道，WhisperFeatureExtractor（80 mel，30s 分块） |
| 输出格式 | `[start][Sxx]text[end]`，如 `[0.48][S01]欢迎[1.66]` |
| 单次时长 | 官方称最长 **90 分钟**单次推理 |
| 热词 | ✅ 默认 prompt 后追加"热词提示：词1, 词2" |
| 声学事件 | ✅ 可选输出（`[笑声]`之类） |
| 荣誉 | INTERSPEECH 2026 第二届 MLC-SLM Challenge 第一名（14 语种） |

**架构上的关键点**：它不是"ASR + 分离"两套系统拼接，而是**一个自回归解码器同时生成"谁在什么时候说了什么"**——说话人标签是生成出来的 token，不是聚类出来的。这解释了它在重叠场景下的优势，也解释了它在时间戳上的不稳定性。

此外，processor 会在音频 token 序列里**每 2 秒插入一个数字时间锚点**（`enable_time_marker`），这是它能出较准时间戳的机制。

## 2. 官方评测（中文多人场景）

指标：CER（字错率）、cpCER（拼接后最小排列字错率）、Δcp（分离质量，越低越好，负值表示分离带来增益）。

| 模型 | AISHELL-4 CER / cpCER / Δcp | Alimeeting | Podcast | Movies |
|---|---|---|---|---|
| Doubao | 18.18 / 27.86 / 9.68 | 25.25 / 37.57 / 12.31 | 7.93 / 10.54 / 2.61 | 9.94 / 30.88 / 20.94 |
| Gemini 3 Pro | 22.75 / 27.43 / 4.68 | 26.75 / 32.84 / 6.09 | — | 8.62 / 14.73 / 6.11 |
| **MOSS 0.9B** | **14.84 / 15.83 / 0.99** | **24.86 / 22.17 / −2.69** | **5.97 / 7.37 / 1.40** | **6.36 / 12.76 / 6.40** |
| MOSS Pro（闭源） | 13.78 / 14.02 / 0.24 | 18.22 / 13.94 / −4.27 | 4.46 / 6.97 / 2.51 | 5.86 / 11.78 / 5.92 |

⚠️ **不能直接和我们测的 Paraformer 10.18% 比**：那是 FunASR 自己的 184 文件基准，语料与切分方式不同。上表内部可比（同一评测集、同一指标），跨表不可比。

值得注意的 **Alimeeting Δcp = −2.69**：意思是"先做说话人排列再算错率"比"不排列"还低——说明它的说话人标签不仅准，还能帮助文本对齐。这对我们"按说话人列出"的需求是直接的正面信号。

## 3. 本机实测

### 3.1 环境

transformers 5.22.1 + torch 2.6.0（CPU fp32），`trust_remote_code=True`，`attn_implementation="sdpa"`。
模型 1.82GB，从 hf-mirror 下载（**必须 `HF_HUB_DISABLE_XET=1`**，且 `HF_MODULES_CACHE` 要指向可写目录，否则 `PermissionError: ~/.cache/huggingface/modules`）。

### 3.2 速度与资源

| 音频 | 时长 | 生成耗时 | RTF | 实时倍速 | 输出 token | tok/s | 峰值 RSS |
|---|---|---|---|---|---|---|---|
| 冒烟片段 | 8.0s | 4.86s | 0.608 | 1.65× | 41 | 8.43 | 4.70GB |
| 3 人无重叠 | 39.57s | **18.57 / 20.55s**（两次） | 0.47–0.52 | **1.93–2.13×** | ~230 | 11–12.4 | 5.66–5.9GB |
| 重叠样本 | 23.06s | **12.14 / 13.51s**（两次） | 0.53–0.59 | **1.71–1.90×** | 153 | 11.3–12.6 | 5.66GB |
| 重叠窗口 | 13.0s | 8.86s | 0.682 | 1.47× | ~90 | — | — |
| 3 人（**MPS**） | 39.57s | 25.21s | 0.637 | **1.57×** | — | 8.17 | 5.66GB |

**三个观察**：

1. **MPS（Apple GPU）比 CPU 更慢**（25.21s vs 18.57s）。小模型 + 逐 token 自回归，每个 token 都要几十次 kernel launch，GPU 调度开销压过了算力优势。**这台机器上跑 MOSS 就用 CPU。**
3. **同一输入两次运行有 ~10% 的耗时波动**（CPU 调度/热节流），因此下文一律给区间而非单点。
2. **内存 5.7GB**，高于 0.9B 模型的直觉预期——音频特征（30s 分块 × 80 mel）+ KV cache 是大头。transcribe.cpp 文档给的估算是一致的：**每音频分钟额外 ~85MB**（30 分钟 ≈ 2.5GB，1 小时 ≈ 5GB）。

### 3.3 质量对比（同一段 39.57s，3 人会议）

**FunASR（现状）**
```
[22.67-24.47] S2: 我补充一下数据平台这边我们已经认批，
[24.47-25.43] S2: 他做了标准查询，
[26.45-28.55] S2: 但是我担心经营期间的收息会带来一致性问题。
```

**MOSS（无热词）**
```
[S01] …第一是第四季度的交付节奏，第二是数据平台的迁移方案，第三是下个月的招聘计划。
[S02] 我先说一下交付的问题…主要是接口连掉卡住了…
[S01] 我补充一下，数据平台这边我们已经用KPI做了压测…我担心迁移期间的双写会带来一致性问题。
```

**MOSS（加热词 `ClickHouse, 联调, 双写, 灰度, 招聘`）**
```
[S01] …第二是数据平台的迁移方案…
[S02] …主要是接口联调卡住了…
[S01] 我补充一下，数据平台这边我们已经用 ClickHouse 做了压测，查询性能提升了大概三倍。
      但是我担心迁移期间的双写会带来一致性问题。
[S02] 好，那这样，交付这块拟出一个风险清单，周五之前给我。数据迁移就先做灰度，招聘的事情我下周跟人事对齐。
```

**逐项对照（真值 vs 两方案）**

| 真值 | FunASR | MOSS（热词） |
|---|---|---|
| 迁移方案 | 交移方案 ❌ | 迁移方案 ✅ |
| ClickHouse | 认批 / 标准查询 ❌ | ClickHouse ✅ |
| 联调 | 连调 ❌ | 联调 ✅ |
| 双写 | 收息 ❌ | 双写 ✅ |
| 灰度 | 灰度 ✅ | 灰度 ✅ |
| 你出一个风险清单 | 拟出一个风险清单 ❌ | 拟出一个风险清单 ❌ |

→ **热词把我们的头号痛点（中英混说专名）基本解决了**；但"你→拟"这类同音/近音错误两者都没解决，仍需 LLM 纠错兜底。

### 3.4 重叠说话（决定性对比）

同一段 23.06s、两人同时说 4–11.6s 的音频：

**FunASR**：两人词缝成一句，整体归一人
```
[4.13-8.11] S1: 第一是那这一季度的交付结在你出一个风险清单，
[11.99-14.91] S1: 我先说一下前我下的问题跟人事对齐，
```

**MOSS**：
```
[0.07][S01]各位同事，我们今天的周会主要讨论三件事，第一是第四季度的交付节奏，
           第二是数据平台的迁移方案，第三是下个月的招聘计划。[11.81]
[3.98][S02]好，那这样，交付这块拟出仪的风险清单，周五之前给我，数据迁移就先做灰度，
           我先说一下交付的问题，目前我们有两个模块的进度…我觉得需要加一个人手。[23.03]
[12.12][S02]招聘的事情我下周跟人事对齐。[14.95]
```

**怎么读这个结果**：

| 维度 | 判定 |
|---|---|
| 内容分离 | ✅ **明显更好**：S01 段里完全没有李四的词，S02 段里没有张三的词——这是 FunASR 做不到的 |
| 说话人归属 | ✅ 正确（S01=张三、S02=李四，各自内容完整） |
| **时间戳** | ❌ **乱序**：`[11.81]` 后接 `[3.98]`，三段区间互相重叠，最后一段 `[12.12–14.95]` 出现在 `[23.03]` 之后 |
| 重叠标记 | ❌ 不输出"这里有人重叠"，只是把两段并列生成 |

**为什么会这样**：自回归生成说话人标签时，模型"知道"有两个人在说、也能分别解码出各自的内容；但时间戳是它**逐段生成的数字**，在多线程并行的语音里，它无法保证输出的时间单调递增。**内容可信，时间轴不可信**——这是关键结论。

**窗口重转写测试**（截 3–16s，13 秒）：
```
[0.07][S01]论三件事，第一是第四季度的交付节奏，第二是数据平台的迁移方案，第三是下个月的招聘计划。[9.01]
[1.01][S02]好，那这样。[2.11]
[2.98][S02]你出仪的风险清单，周五之前给我，数据迁移就先做灰度，我先说一下交付的问题…[12.94]
```
→ 结论：**只对重叠窗口重跑是可行的**（13s 窗口 8.86s），两人内容依然分得清；但窗口边界会把句子切断（"论三件事"少了"讨"），所以窗口要留 2–3 秒余量。时间戳同样是乱序的，需要我们自己重映射。

### 3.5 更快路径（未在本机验证）

| 路径 | 事实 | 状态 |
|---|---|---|
| **GGUF + Metal**（transcribe.cpp） | Q4_K_M 仅 **617MB**、Q8_0 987MB；**Apple M4 Max** 上 Q8_0 **28.3×**、Q4_K_M **29.8–30.1×** 实时（英文样本） | 未验证（GitHub 不通，无法编译 runtime） |
| **funasr-mlx**（MLX 原生） | 0.2.3 覆盖 MOSS，W4A16 量化在 M4 上降内存 41–59%、解码快至 2.7× | 未验证 |
| vLLM / SGLang Omni | 官方推荐的生产后端，H100 上长音频 RTF 0.0197 | 需 CUDA，不适用 |

> M4 Max 与基础 M4 差一个档次，按 1/3 折算，基础 M4 上 Metal 路径可能落在 **9–10× 实时**——这仍是当前 CPU 路径（2.1×）的 4–5 倍，值得做 PoC。

## 4. 对我们的项目意味着什么

### 4.1 能直接用的（建议采纳）

| # | 用法 | 收益 | 成本 |
|---|---|---|---|
| **1** | **重叠区间二次转写**（替换原 VoxLock 方案） | 重叠段从"乱码"变成"两人各自完整的话" | 按重叠时长计费，实测 RTF 0.5–0.68 |
| **2** | **热词注入** | 专名/英文术语正确率质变 | 零成本，改 prompt |
| **3** | **高质量模式**（可选，全量用 MOSS） | 文本质量与标点明显优于现状 | 1 小时会议约 28 分钟（CPU） |
| **4** | **作为纠错的"参考答案"** | 对低置信度片段，用 MOSS 重跑一次对照 | 按片段计费 |

### 4.2 不能替代的

1. **速度**：约 1.5–2× 实时，1 小时会议约 **30 分钟**，**不满足 PRD 的"≤12 分钟"**。FunASR 的 21× 仍是硬优势。
2. **时间戳**：正常段落够用，**重叠段落不可用**。混合方案里必须做时间重映射。
3. **声纹认名**：它只给匿名 `[S01]`，注册式声纹仍要 CAM++。

### 4.3 关键设计：混合流水线（建议）

```
FunASR 全量转写（21× 实时）
   ├─ 正常段 → 直接采用（文本 + 精确时间戳）
   └─ 重叠段（由 FR-C6 检测）
        └─ 截取 ±3s 窗口 → MOSS 重转写
              ├─ 采用 MOSS 的文本与说话人（内容更可信）
              └─ 时间戳用 FunASR/VAD 的边界重映射（MOSS 的时间不可信）
```

**为什么这个组合成立**：重叠在真实会议里占比通常 <10%，按 1 小时会议里 20 段 × 10 秒重叠计，MOSS 额外耗时 ≈ 200s × 0.6 ≈ **2 分钟**，总时长仍在 12 分钟预算内。

### 4.4 与 VoxLock 方案的对比（结论：换掉）

| 方案 | 重叠段效果（实测） | 每段成本 | 结论 |
|---|---|---|---|
| VoxLock 目标提取 | 提取后仍残留对方内容，新增错误 | 5.8× 实时 × 2 次（每人一次） | ❌ 降级为备选 |
| **MOSS 窗口重转写** | 两人内容分开、说话人正确 | 1.5–2× 实时 × 1 次 | ✅ **采纳** |

## 5. 风险与限制

| # | 风险 | 说明 | 缓解 |
|---|---|---|---|
| R1 | 中文真实会议未评测 | 本机测试用 TTS 合成音，官方评测是 AISHELL-4/Alimeeting（真实但非本项目场景） | 用基准集实测，不照抄官方数字 |
| R2 | 时间戳在重叠/长音频下可能漂移 | 自回归生成数字，无强约束 | 混合方案中只用其文本，时间用 VAD 重映射 |
| R3 | 幻觉风险 | 音频-LLM 可能在静音/噪声处"脑补" | 与 VAD 结果交叉校验，无语音段强制丢弃 |
| R4 | 依赖 transformers 5.x + trust_remote_code | 升级可能破坏；需锁定版本 | 固定版本 + 冒烟测试进 CI |
| R5 | 内存 5.7GB | 与 9B LLM 不能共存 | 阶段串行，用完卸载 |
| R6 | 本机下载需绕开 HF 直连 | Xet 协议 401、模块缓存目录不可写 | 文档已记录（`HF_HUB_DISABLE_XET=1`、`HF_MODULES_CACHE`） |
| R7 | GGUF 路径未验证 | 速度优势是标称值，芯片不同 | 单独立项 PoC，验证前不写进主线 |

## 6. 建议的落地顺序

| 阶段 | 动作 | 产出 | 工时 |
|---|---|---|---|
| P0（本周） | 把 MOSS 接成 `asr.provider` 的可选项，先只用于**重叠窗口** | `engines/moss_asr.py` + 窗口截取 + 时间重映射 | 2–3 天 |
| P0 | 热词从 `glossary.yaml` 注入 MOSS prompt | 与 FunASR 共用术语表 | 0.5 天 |
| P1 | 基准集上做 A/B（FunASR vs MOSS vs 混合），统计 CER 与说话人准确率 | 对比报告 | 1–2 天 |
| P2 | GGUF + Metal PoC（3 个量化档位，测 RTF 与 CER） | 若 ≥8× 再考虑提为主引擎 | 2 天 |

```bash

export HF_ENDPOINT=https://hf-mirror.com HF_HUB_DISABLE_XET=1

# 下载（1.82GB）
python -c "from huggingface_hub import snapshot_download; snapshot_download('OpenMOSS-Team/MOSS-Transcribe-Diarize', local_dir='.cache/moss')"

# 推理（CPU）
python bench/bench_moss.py bench/in/meeting_sample.wav 1024
MOSS_HOTWORDS="ClickHouse, 联调, 双写" python bench/bench_moss.py bench/in/meeting_sample.wav 1024
MOSS_DEVICE=mps python bench/bench_moss.py bench/in/meeting_sample.wav 1024   # 更慢，仅对照
```
