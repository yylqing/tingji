> 日期 2026-10-31｜样本：一段 73 分钟真实会议录音（1:12:55，AAC 44.1kHz 立体声）
> 目的：用**真实多人会议**验证技术路线，暴露合成音频测不出的问题
> 原始产物（逐字稿/诊断报告）为本地生成，未随仓库发布

## 2. 暴露的四个问题（合成音频测不出来）

### 2.1 说话人过度聚类：10 簇 → 实际约 7 人

| 事实 | 数据 |
|---|---|
| 原始聚类 | 10 个簇，其中 4 个簇时长 <1 分钟 |
| 高相似簇对 | S1~S8 **0.852**、S4~S7 0.734、S5~S7 0.715 |
| 短句占比 | **30.1% 的句子 <1 秒**（538/1788） |
| 修复合计 | 合簇 + `<1s` 回填 → 10 簇降到 7 簇 |

**根因**：短句的 CAM++ 向量极不稳定，聚类把同一人的碎片分到不同簇，又把句子从中间切断（例：`说话人3: 就基于这张图…` / `说话人1: 的，需求就是…`）。

**设计修正**：
- 参与聚类的句子必须 **≥1 秒**，更短的继承邻句说话人（P0）；
- 聚类结果必须做**质心相似度合并**（≥0.72 连通分量），而不是直接展示原始簇（P0，原为 P1）。

### 2.2 超长 VAD 段导致标点崩溃

| 事实 | 数据 |
|---|---|
| 最长单段 | **280.7 秒** |
| 该段输出 | 仅 16 字 |
| 单字被标点包夹 | **147 处**（"这，个东西"、"然？后"） |

**根因**：`CT-Punc` 对整段做标点，段越长退化越严重。VAD 在连续独白处不切分。

**设计修正**：VAD 段 **>30s 强制二次切分**（按能量谷），逐段做 ASR 与标点（P0）。

### 2.3 11% 的音频没有可靠输出

| 事实 | 数据 |
|---|---|
| `>10s 且 <1 字/秒` 的段 | 10 段，合计 **8.2 分钟（11.2%）** |
| 语速正常（≥3 字/秒）的覆盖 | 51.9 分钟（71.2%） |
| 最严重 | 25.4min 处 280.7s 只出 16 字 |

**设计修正**：新增**低质量段过滤**——`<1 字/秒 且 >10s` 的段标记 `low_quality`，不进正文、不计入说话人统计、UI 提示"此处建议回听"。

### 2.4 英文术语系统性错识（热词的最佳用例）

| 识别 | 正确 | 次数 |
|---|---|---|
| `sars` | **SaaS** | 12 |
| `口顶` | **Copilot** | 1–2 |
| `Infinity Band` | **InfiniBand** | 2 |
| `firewer` | **firewall** | 2 |
| `办卡服务器` | **八卡服务器** | 1 |
| `SCP` | **CSP**（云服务商，待确认） | 1 |

同时确认正确的：`IDC`、`KYC`、`NCP`、`AIDC`、`POC`、`IAM`、`VPN`、`AIGC`、`API`。

**设计修正**：无需改设计——这正是 [热词三层注入](../05-热词登记设计.md) 要解决的，验证了 L1+L2 的必要性。

## 2.5 全量纠错实测（补充）

对全部 20,771 字做逐批纠错（qwen3.5:9b-q4_K_M，350 批）：

| 指标 | 值 |
|---|---|
| 批次 | 350（按"发言块内连续句子"切分，约 60 字/批） |
| 总耗时 | **1434 秒（23.9 分钟）** |
| 单字成本 | **0.069 秒/字** |
| 产出 | [纠错稿](../../output/archive/reports/会议录音-纠错稿.md)（322/348 个发言块） |

**质量变化（全量统计）**

| 指标 | 原始 | 纠错稿 |
|---|---|---|
| 字数 | 22,255 | 20,011（−10%） |
| 嗯/呃/啊 | 368 | **69**（−81%） |
| 那个 | 279 | **84**（−70%） |
| `sars` | 12 | **0** |
| `SaaS` | 0 | **23** |

**时间戳**：纠错稿保留**段落级**时间（324 段，全部由 ASR 句子边界推导，0 处重叠，覆盖 64.3/65.3 分钟），但**不保留句子级**——LLM 改写了句子边界。需要逐句时间时看原文轨（1,788 句）。

**踩到的坑**：模型对"纯标点/噪声"输入会输出**解释性文字**（"由于您提供的原文仅包含标点符号…"）。350 批中触发 17 次；另有 26 批原文本身无实质内容。必须在调用前过滤短输入、调用后检测元评论并回退原文——已写入 [开发方案 §4.4](../06-开发方案.md)。

**效果**（同一段对比）：

| 原始 | 纠错后 |
|---|---|
| `一个 mut 哦，我刚 mute 掉了` | 一个会议中我刚才误触了静音，现在恢复一下 |
| `sars 的 spider 的服务` | SaaS 的 Spider 服务 |
| `infinity band` | **InfiniBand** |
| `本地 coding 使用口，顶的时候` | 本地使用 **Copilot** 时 |
| `两台办卡服务器` | 两台**办卡**服务器（仍错，应为"八卡"，需热词） |

**发现**：切批粒度影响效率——350 个小批（均值 60 字）中有大量固定开销；按 700 字打包可减少调用次数，但生成时间占比更高，总耗时相近（约 0.06–0.07 秒/字）。
**结论**：1 小时音频的纠错约需 **9–10 分钟**，必须做选择性纠错或提供 `fast` 模式。

## 3. 对照：LLM 纠错的实际效果

取 00:01:06–00:06:30（1,989 字）跑 qwen3.5:9b：

| 项 | 值 |
|---|---|
| 输出 | 1,023 字（压缩 49%） |
| 耗时 | 50.4s（551 token，14.3 tok/s） |
| 修正 | `sars→SaaS`、去填充词、标点正常 |
| **副作用** | **被改写成"分点结构"**，破坏了与原音频的逐句对应 |

**结论**：整段交给 LLM 只能产出"可读版"，不能当逐字稿。逐字稿的纠错必须**按 seg_id 逐句**进行并做长度变化率校验（PRD FR-D3 已约束）。这是本轮最重要的实证。

## 4. 对技术路线的影响

| 项 | 原判断 | 真实数据后 |
|---|---|---|
| FunASR 做主引擎 | ✅ | ✅ **成立**，12.8× 实时 |
| 句级聚类足够 | ⚠️ | ❌ **需补丁**：短句不聚类 + 簇合并 + 长段切分 |
| 标点用 CT-Punc | ✅ | ⚠️ 仅在**短段**上可靠，长段必须切分 |
| 热词必要 | ✅ | ✅ **强烈验证**（`sars` 错了 12 次） |
| LLM 纠错边界 | 需约束 | ✅ **必须按句约束**，否则破坏时间轴 |
| MOSS 全量 | 可选 | 暂不适用（73 分钟需约 38 分钟，且无 ground truth 对比） |
